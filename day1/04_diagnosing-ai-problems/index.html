03

Four root causes, line-cited

"The prompt seems off" isn't evidence. These point at the exact lines.

🔀

1 · Single-dispatch routing

A ticket is treated as exactly one category, so multi-issue tickets structurally lose everything but the primary issue.

coordinator prompt: step 5 "Call spawn_specialist with the right category" (singular) · classifier "If a ticket could fit two categories, pick the one the customer seems most blocked by." The spawn_specialist enum takes one category, no loop.
🎭

2 · Over-claiming + a dead escalation path

The specialist reported "Both issues handled" when it handled one, and the coordinator marked the ticket resolved. The escalation tool that exists for exactly this was never touched.

account subagent trace: returns "Both issues handled" → then "outside what I can action directly." · coordinator tools: escalate_to_human exists with reasons security / customer_escalation — never called. Subagents don't even have it.
🏷️

3 · Tool descriptions written for the backend, not the model

The metrics tool names its warehouse, not its use case — so the model never knows to reach for it. Plus ~9 vague/duplicate tools cause decision paralysis, wrong picks, and wasted calls.

coordinator tools: fetch_customer_v2_databricks = "Queries the Databricks warehouse. v2, use this not the old one." · junk: get_data "Gets data", helper "General helper function", process, validate, tool_3_v2. Trace burned 3 calls to identify one customer.
💾

4 · Caching wired backwards (the "no savings")

Volatile tokens sit at the front of the cached prefix, so the prefix changes every request and the cache never hits.

coordinator prompt lines 1–2: Current timestamp: {{ }} · Request ID: {{ }} — before the stable instructions. Trace usage: cache_read_input_tokens: 0.
04

One-liner per agent

The tried-and-tested move for each — and why the subagents aren't actually the problem.

Coordinator

🧭 The real bottleneck

● Needs the structural fix
Classify to multiple labels and loop spawn_specialist until every distinct issue is actioned or escalated — then add a verification gate so resolved requires every issue to map to a tool action.
Account specialist

🔐 Honest, not broader

● Add an honesty contract
"Only claim resolved what you actioned with a tool; return everything else as UNRESOLVED + next step — never invent customer-facing advice." Give it escalate_to_human.
Billing specialist

💸 Never even reached

● Scope is fine
It has issue_refund + adjust_invoice — it just never got spawned. Fixing the coordinator's routing fixes this one for free. Add: state the refund/credit ID or escalate.
Technical specialist

🚦 Blind to its own metrics

● Wrong tool placement
"Check actual error/retry metrics before concluding 'within limits'" — and move the stranded metrics tool off the coordinator onto this agent.
05

Write tool descriptions for the decision

The single highest-leverage cheap fix. Describe when I'd reach for this, not the plumbing.

fetch_customer_v2_databricks "Queries the Databricks warehouse. v2 endpoint, use this not the old one." ✗ Names the backend, not the use case. No trigger condition. Model can't tell this is the metrics tool — so it stays unused.
get_usage_and_error_metrics "Fetch a customer's real request volume, error rates, and retry behaviour per endpoint. Use this whenever a customer reports rate limiting, throttling, 429s, slow responses, or a usage anomaly — before quoting their plan limits." ✓ Capability-named. States the trigger. Gives examples. Now it gets called.

Then delete the dead weight: get_data, helper, process, validate, customer_data_retrieval, tool_3_v2, and collapse get_customer / fetch_customer_details / lookup_customer_info into one well-described lookup. Fewer, sharper tools = fewer wrong picks, fewer tokens, faster resolutions.

07

Better ways to work it

You asked about hooks, plugins, MCP, Bluesky. Here's the honest ranking.

★ BEST FIT
🔌

MCP server

Wrap tickets, billing, SSO & metrics as one MCP server with capability-named, trigger-rich tool descriptions. Kills the duplicate-tool sprawl; enforces good descriptions at the source.

★ GUARDRAIL
🪝

Validation hook

A pre-write_response / Stop hook that programmatically blocks resolved when any ticket issue is unactioned. Don't trust the prompt to be honest — enforce it in code.

PACKAGING
📦

Plugin

Bundle prompts + tool defs + the hook + an eval suite into one versioned plugin, shared across all 11 customers. Fix once, ship everywhere.

✗ NOT THIS
🦋

Bluesky

It's a social network / AT-Protocol — no role in an internal support pipeline. Tempting name, wrong tool. Leave it out.

🔭 And the early-warning layer Priya actually wants

Add observability + evals: an LLM-as-judge that asks "did every issue in the ticket get resolved or escalated?", and an alert that fires when a ticket is closed resolved with an unactioned issue. That's how "make sure these don't come back" becomes measurable instead of hopeful.

08

The ship list

In leverage order — lights up as you reach it.

  • Multi-route the coordinator — classify to N labels, loop dispatch until every issue is actioned or escalated.
  • Add a verification gate — resolved only if every distinct issue maps to a tool action; else needs_info / escalate_to_human.
  • Rewrite tool descriptions for triggers, rename by capability, and delete the ~9 junk/duplicate tools.
  • Give subagents an honesty contract + escalation tool — never invent advice for out-of-scope work.
  • Move the metrics tool onto the technical specialist and require checking real metrics before quoting limits.
  • Reorder the prompt for caching — stable instructions/tools first, volatile timestamp/request_id last.
  • Stop adding single-issue examples — add one multi-issue + one escalation example instead.
  • Wrap it in an MCP server + validation hook + eval harness for the durable fix.
